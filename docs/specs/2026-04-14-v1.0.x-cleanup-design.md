### 1. Issue #13 — `git_cli.parse_origin_url` ssh:// support

**Problem**: The current implementation uses 2 regex constants:

```python
_SSH_RE = re.compile(r"^git@github\.com:([\w.\-]+)/([\w.\-]+?)(?:\.git)?/?$")
_HTTPS_RE = re.compile(r"^https://github\.com/([\w.\-]+)/([\w.\-]+?)(?:\.git)?/?$")
```

These only accept SCP-form SSH (`git@github.com:owner/repo`) and HTTPS, rejecting valid `ssh://` URL forms used by users behind restrictive firewalls or with non-default SSH configs:

- `ssh://git@github.com/owner/repo.git` (explicit ssh:// scheme)
- `ssh://git@ssh.github.com:443/owner/repo.git` (SSH-over-port-443 alternate hostname)

**Approach**: Hybrid — special-case for SCP-form (urllib.parse cannot handle no-scheme URLs), then `urllib.parse.urlparse` for everything else.

```python
from urllib.parse import urlparse

_SCP_FORM = re.compile(r"^git@([\w.\-]+):(.+)$")
_PART_RE = re.compile(r"^[\w.\-]+$")
_ALLOWED_HOSTS = ("github.com", "ssh.github.com")
_ALLOWED_SCHEMES = ("https", "ssh")  # NOT 'git' — the git:// read-only
                                       # protocol is unused by gh-manage and
                                       # untested. Add only when a real
                                       # consumer requests it.

def parse_origin_url(url: str) -> str:
    """Parse a git remote URL into 'owner/repo' form. Pure.

    Supports GitHub only (github.com or ssh.github.com):

      git@github.com:owner/repo[.git]                      → owner/repo
      https://github.com/owner/repo[.git]                  → owner/repo
      ssh://git@github.com/owner/repo[.git]                → owner/repo
      ssh://git@ssh.github.com:443/owner/repo[.git]        → owner/repo

    Raises ValueError on any other form (gitlab, bitbucket, self-hosted,
    malformed) with an actionable message naming the offending URL.
    """
    # Step 1: SCP-form normalization
    if (scp_match := _SCP_FORM.match(url)) is not None:
        host, path = scp_match.groups()
        url_to_parse = f"ssh://git@{host}/{path}"
    else:
        url_to_parse = url

    # Step 2: parse via urllib
    parsed = urlparse(url_to_parse)

    # Step 3: validate scheme
    if parsed.scheme not in _ALLOWED_SCHEMES:
        raise ValueError(
            f"Unsupported git remote URL: {url!r}. "
            f"Scheme {parsed.scheme!r} is not supported. "
            f"gh-manage only supports github.com origins via https, ssh, or git@."
        )

    # Step 4: validate host
    host = parsed.hostname or ""
    if host not in _ALLOWED_HOSTS:
        raise ValueError(
            f"Unsupported git remote URL: {url!r}. "
            f"gh-manage only supports GitHub (github.com) origins. "
            f"Non-GitHub remotes (gitlab.com, bitbucket.org, self-hosted) "
            f"are not supported."
        )

    # Step 5: extract and clean path
    path = parsed.path.lstrip("/").removesuffix("/").removesuffix(".git")
    parts = path.split("/")
    if len(parts) != 2 or not all(parts):
        raise ValueError(
            f"Unsupported git remote URL: {url!r}. "
            f"Cannot extract owner/repo from path {parsed.path!r}."
        )
    owner, repo = parts

    # Step 6: validate owner/repo characters (preserve old regex's strict check)
    if not _PART_RE.match(owner) or not _PART_RE.match(repo):
        raise ValueError(
            f"Unsupported git remote URL: {url!r}. "
            f"owner/repo characters must match [\\w.\\-]+."
        )

    return f"{owner}/{repo}"
```

**Files**:
- Modify: `src/gh_manage/git_cli.py` — replace 2 regex constants and `parse_origin_url` body
- Modify: `tests/unit/git_cli/test_*.py` (locate the existing test file in implementation phase) — add 13 new test cases (8 positive + 5 negative)

**Tests** (TDD):

Positive (parametrized, 8 cases):
- `git@github.com:owner/repo.git` → `owner/repo`
- `git@github.com:owner/repo` → `owner/repo`
- `https://github.com/owner/repo.git` → `owner/repo`
- `https://github.com/owner/repo` → `owner/repo`
- `ssh://git@github.com/owner/repo.git` → `owner/repo`
- `ssh://git@github.com/owner/repo` → `owner/repo`
- `ssh://git@ssh.github.com:443/owner/repo.git` → `owner/repo`
- `ssh://git@ssh.github.com:443/owner/repo` → `owner/repo`

Negative (parametrized, 6 cases):
- `git@gitlab.com:owner/repo.git` → ValueError (non-github host)
- `https://gitlab.com/owner/repo.git` → ValueError (non-github host)
- `https://bitbucket.org/owner/repo.git` → ValueError (non-github host)
- `ssh://git@self-hosted.example.com/owner/repo.git` → ValueError (non-github host)
- `https://example.com/owner/repo.git` → ValueError (non-github host)
- `git@github.com:443:malformed` → ValueError (SCP-form normalization produces `ssh://git@github.com/443:malformed`, then path split fails because the path after `lstrip("/")` is `443:malformed` — only 1 segment, not 2). This case verifies the SCP-form regex's greedy second capture (`(.+)`) is safely caught downstream by the `len(parts) != 2` check at Step 5, not silently accepted as a degenerate parse.

**SCP-form edge case note**: the `_SCP_FORM` regex `^git@([\w.\-]+):(.+)$` greedily captures everything after the first `:` as the path. For inputs like `git@host:443:extra` (which a user might mistype while trying to use SSH-over-port-443), the second capture group becomes `443:extra`. After SCP normalization, this becomes `ssh://git@host/443:extra`, and `urlparse` sets `parsed.path = "/443:extra"`. The path-split logic at Step 5 then sees 1 segment instead of 2 and rejects with a clear ValueError. The malformed-SCP test case above pins this defense.

**Acceptance**: 4 new positive cases pass (the 4 ssh:// forms), all existing happy paths still pass, all 5 negative cases reject with ValueError, `get_origin_owner_repo` still wraps `ValueError` → `UnsupportedOriginError`.

### 2. Issue #11 — `run_gh_api` POST/PATCH empty stdout silent None

**Problem**: At `src/gh_manage/github_client.py:145-147`:

```python
stdout = run_gh(args, stdin_input=stdin_input)
if not stdout.strip():
    return None
```

For GET (legitimate empty body) and DELETE (legitimately returns no content), this is correct. For POST and PATCH, GitHub's API documents that a successful response returns the created/updated resource, so an empty stdout indicates a silent failure (gh subprocess succeeded but returned nothing). Currently `create_label` / `update_label` ignore the return value and `apply_diff` reports "Applied N changes" even when the operation silently no-oped.

**Approach**: Per-method check at the transport layer.

```python
stdout = run_gh(args, stdin_input=stdin_input)
if not stdout.strip():
    if method in ("GET", "DELETE"):
        return None
    raise GhAPIError(
        f"GitHub API returned empty response for {method} {endpoint}. "
        f"This is unexpected for {method} requests, which should return the "
        f"created/updated resource. Re-run with `GH_DEBUG=api` to inspect "
        f"the raw response."
    )
```

**Files**:
- Modify: `src/gh_manage/github_client.py` — replace 1 if-block in `run_gh_api`
- Modify: `tests/unit/github_client/test_github_client.py` — add 2 new tests

**Tests** (TDD):


### 3. Issue #10 — `github_api/labels.list_labels` NDJSON validation

**Problem**: At `src/gh_manage/github_api/labels.py:65-71`:

```python
labels.append(
    Label(
        name=item["name"],
        color=item["color"].lower(),
        description=item.get("description") or "",
    )
)
```

If GitHub returns valid JSON missing required fields, the user sees a raw `KeyError: 'name'` traceback instead of a `GhAPIError` with actionable context. Wrong types (e.g. `color: 12345`) raise `AttributeError: 'int' object has no attribute 'lower'`. The `description: item.get("description") or ""` pattern silently coerces falsy non-None values like `0` or `False` to `""`.

**Approach**: Define a transient internal pydantic DTO and validate before constructing the public `Label` dataclass.

```python
from pydantic import BaseModel, ValidationError

class _LabelDTO(BaseModel):
    """Transient pydantic model for parsing GitHub labels API NDJSON output.

    Internal to list_labels — NOT exported (leading underscore). The
    caller-facing dataclass is the frozen `Label` defined above. This DTO
    exists only to validate the dict shape coming from `gh api` before
    constructing `Label`.

    Pattern: API response validation uses pydantic models as internal-only
    helpers to catch schema violations early with clear error messages,
    then constructs the public dataclass. This avoids raw KeyError /
    AttributeError / silent type coercion in the error path. If a future
    GitHub API change adds new fields, `extra="ignore"` quietly drops them
    instead of breaking the parser.
    """

    model_config = {"extra": "ignore"}

    name: str
    color: str
    description: str | None = None
```

Then in `list_labels`:

```python
try:
    item = json.loads(line)
except json.JSONDecodeError as e:
    raise GhAPIError(...) from e

try:
    dto = _LabelDTO.model_validate(item)
except ValidationError as e:
    raise GhAPIError(
        f"GitHub API returned malformed label item: {e.errors()}. "
        f"Endpoint: repos/{repo}/labels. "
        f"Raw item: {item!r}. "
        f"Re-run with `GH_DEBUG=api` to inspect the raw response."
    ) from e

labels.append(
    Label(
        name=dto.name,
        color=dto.color.lower(),
        description=dto.description if dto.description is not None else "",
    )
)
```

**Description coercion behavior change**:

| Input | Old behavior | New behavior |
|---|---|---|
| `description=None` | `""` (silent) | `""` (preserved) |
| `description=""` | `""` (preserved) | `""` (preserved) |
| `description="x"` | `"x"` (preserved) | `"x"` (preserved) |
| `description=0` | `""` (silent coercion) | `GhAPIError` (wrong type) |
| `description=False` | `""` (silent coercion) | `GhAPIError` (wrong type) |

This is intentional hardening: silent coercion of unexpected types was a bug, not a feature. In practice, GitHub's API never returns `0` or `False` for description, so this hardening should never fire on real data — it only catches genuine API contract violations or test fixtures.

**Files**:
- Modify: `src/gh_manage/github_api/labels.py` — add `_LabelDTO` class and rewrite the construction loop

| Test file paths under `tests/unit/github_api/` | Issue #10 test changes | `find tests/unit/github_api -name "test_*"` to locate existing label tests file. Same decision rule as above (single match → append; no match → create `tests/unit/github_api/test_labels.py`). |
| `<merge-date>` in `CHANGELOG-cli.md` `[1.0.1]` heading | Bump PR | Use the actual PR merge date (`gh pr view <bump-pr> --json mergedAt`) |
| Existing test count baseline (401) | All tests | Verify with `git checkout main && uv run pytest --tb=no -q | tail -5` before starting; adjust expected count if main has drifted |
